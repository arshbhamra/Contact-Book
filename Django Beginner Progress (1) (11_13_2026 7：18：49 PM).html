Day 12 — Django ModelForms: Connecting Forms to Models

Phase 1 · Django Fundamentals
Day 12 of ~60

Yesterday, you learned how to create forms using forms.Form, validate submitted information and manually save it using Django ORM.

Today, we'll learn something more powerful: ModelForms.

Imagine you have 20 database fields and need to create an HTML form for them. With ordinary Django Forms, you would define each field manually.

But what if Django could generate those fields directly from your database model?

That's exactly what ModelForm does.

By the end of today, your Contact Book will support:

  • Adding contacts.

  • Editing existing contacts.

  • Saving changes to the database.

  • Reusing the same form for creating and updating records.

Part 1 — Theory: Understanding ModelForms

1. The problem ModelForms solve

Let's look at your existing Contact model.

Python
class Contact(models.Model):
name = models.CharField(max_length=100)
phone = models.CharField(max_length=15)
email = models.EmailField()
city = models.CharField(max_length=100)
created_at = models.DateTimeField(auto_now_add=True)

Now imagine creating a form using ordinary Django Forms:

Python
class ContactForm(forms.Form):
name = forms.CharField(max_length=100)
phone = forms.CharField(max_length=15)
email = forms.EmailField()
city = forms.CharField(max_length=100)

Notice something?

We're defining almost the same fields twice:

  1. In models.py.

  2. In forms.py.

This creates duplication.

If you change the email field in your model, you might also need to update your form manually.

As applications grow, duplicated definitions become harder to maintain.

ModelForms reduce this duplication by deriving form fields from an existing model.

2. What exactly is a ModelForm?

A ModelForm is a Django form class connected to a database model.

It can automatically:

  • Generate form fields from model fields.

  • Apply model-related validation.

  • Validate submitted information.

  • Create database records.

  • Update existing database records.

Think of it this way:

Django Model

Contact — database structure

ModelForm

Generates fields and validation rules

HTML Form

User enters information

Database

Creates or updates records

The model acts as the source of truth for the database-related fields.

3. How does ModelForm work internally?

A ModelForm combines two things:

A. Form functionality

It inherits the form functionality Django already provides, including:

  • Data binding.

  • Validation.

  • Error handling.

  • cleaned_data.

B. Model functionality

It also understands the connected model.

For example, Django knows that:

  • name is a CharField.

  • email is an EmailField.

  • created_at is automatically populated.

  • The model has a primary key.

It uses this information to generate appropriate form fields and handle model-related validation.

One important distinction: ModelForms do not replace models. They provide a form interface for working with models.

Part 2 — Practical: Create Your First ModelForm

4. Create the ModelForm

Open contacts/forms.py.

Replace your previous ContactForm with:

Python
from django import forms
from .models import Contact


class ContactForm(forms.ModelForm):

class Meta:
model = Contact
fields = ["name", "phone", "email", "city"]

Let's understand every part.

Code

Meaning

forms.ModelForm

Creates a model-connected form

class Meta

Provides configuration for the form

model = Contact

Connects the form to Contact

fields

Specifies which model fields to include

What is the Meta class?

Meta is an inner configuration class.

It provides information that Django uses to configure the outer class.

Here, we're telling Django which model to use and which fields should appear in the form.

Why didn't we include created_at?

Because it uses:

Python
auto_now_add=True

Django automatically sets that field when the record is first created.

The user doesn't need to enter it manually.

Why explicitly specify fields?

Imagine your model later contains:

Python
is_verified = models.BooleanField(default=False)

You probably don't want users to control that field themselves.

Explicitly choosing form fields prevents accidentally exposing model fields that should remain under backend control.

Avoid blindly using:

Python
fields = "__all__"

in user-facing forms unless you have carefully considered every model field.

Part 3 — Understanding the Two Important Operations

5. Creating a record with form.save()

With an ordinary Django Form, you had to manually write:

Python
data = form.cleaned_data

Contact.objects.create(
name=data["name"],
phone=data["phone"],
email=data["email"],
city=data["city"]
)

With a ModelForm, you can simply write:

Python
form.save()

Why?

Because Django already knows which model the form is connected to and which fields belong to it.

The .save() method creates a model instance and saves it to the database.

6. What is instance=?

This is one of the most important concepts today.

Consider two situations:

Situation A: Create a new contact

You want to add Rahul to the database.

Python
form = ContactForm(request.POST)

No existing model object is provided.

Django treats this as a new record.

Situation B: Edit an existing contact

You want to change Rahul's city.

Python
contact = Contact.objects.get(id=1)

form = ContactForm(request.POST, instance=contact)

Here, we're passing an existing database object to the form.

Django understands that the form should update that record instead of creating a new one.

Without instance=

Create

ContactForm(request.POST)

Creates a new Contact when saved.

With instance=

Update

ContactForm(request.POST, instance=contact)

Updates the existing Contact when saved.

This means you can use the same form class for both operations.

7. GET and POST when editing

When editing a contact, two different things happen.

GET request:

The user opens the edit page. Django retrieves the existing contact and displays its current information.

Python
contact = Contact.objects.get(id=1)

form = ContactForm(instance=contact)

POST request:

The user changes the information and submits the form.

Python
form = ContactForm(request.POST, instance=contact)

if form.is_valid():
form.save()

The instance tells Django which existing record to update.

Part 4 — Build the Complete CRUD Form Workflow

Now let's connect everything.

8. Create the Add Contact view

Open contacts/views.py.

Python
from django.shortcuts import render, redirect, get_object_or_404
from .models import Contact
from .forms import ContactForm


def add_contact(request):

if request.method == "POST":

form = ContactForm(request.POST)

if form.is_valid():
form.save()
return redirect("contacts")

else:
form = ContactForm()

return render(
request,
"contacts/add_contact.html",
{"form": form}
)

Understand the flow:

  1. GET → create an empty form.

  2. POST → bind submitted data.

  3. Validate the form.

  4. Save the model.

  5. Redirect after successful submission.

  6. If validation fails, display the form again with errors.

Notice that we no longer need to manually extract every field.

9. Create the Edit Contact view

Add another function to views.py:

Python
def edit_contact(request, pk):

contact = get_object_or_404(Contact, pk=pk)

if request.method == "POST":

form = ContactForm(request.POST, instance=contact)

if form.is_valid():
form.save()
return redirect("contacts")

else:
form = ContactForm(instance=contact)

return render(
request,
"contacts/edit_contact.html",
{"form": form, "contact": contact}
)

Let's understand a new function:

get_object_or_404()

Python
contact = get_object_or_404(Contact, pk=pk)

This tries to retrieve a Contact with the supplied primary key.

If it exists, Django returns the object.

If it doesn't exist, Django raises an HTTP 404 response.

Why is this useful?

Imagine someone opens:

Plain text
/edit-contact/9999/

But contact 9999 doesn't exist.

Instead of displaying an unhandled error, Django returns a proper Not Found response.

What is pk?

pk stands for Primary Key.

Django automatically creates a primary key for your model if you haven't defined one.

You can use pk instead of writing id explicitly.

Part 5 — Templates and URLs

10. Reuse the same form structure

Create or update:

contacts/templates/contacts/add_contact.html

HTML
{% extends 'contacts/base.html' %}

{% block title %}
Add Contact
{% endblock %}

{% block content %}

<h2>Add Contact</h2>

<form method="POST">
    {% csrf_token %}

    {{ form.as_p }}

    <button type="submit">Save Contact</button>
</form>

{% endblock %}

Now create:

contacts/templates/contacts/edit_contact.html

HTML
{% extends 'contacts/base.html' %}

{% block title %}
Edit Contact
{% endblock %}

{% block content %}

<h2>Edit {{ contact.name }}</h2>

<form method="POST">
    {% csrf_token %}

    {{ form.as_p }}

    <button type="submit">Update Contact</button>
</form>

{% endblock %}

Notice that both templates use the same ModelForm.

The difference is that the edit page receives an existing contact instance.

11. Configure the URLs

Open contacts/urls.py.

Add:

Python
urlpatterns = [
path('add-contact/', views.add_contact, name='add_contact'),

path(
'edit-contact/<int:pk>/',
views.edit_contact,
name='edit_contact'
),
]

Make sure you have the necessary imports:

Python
from django.urls import path
from . import views

Your edit URL now accepts a dynamic primary key.

For example:

Plain text
/edit-contact/1/ /edit-contact/2/ /edit-contact/3/

Each URL refers to a different contact.

Part 6 — Advanced Concept: commit=False

You now know that:

Python
form.save()

saves a record directly.

But sometimes you want to modify the model object before saving it.

That's where commit=False becomes useful.

Example:

Python
contact = form.save(commit=False)

contact.city = "Delhi"

contact.save()

Let's understand what happens:

  1. Django validates the form.

  2. form.save(commit=False) creates or updates the model instance in memory.

  3. The database is not written yet.

  4. You modify the object.

  5. .save() persists the changes.

Important distinction:

Code

What happens

form.save()

Saves immediately

form.save(commit=False)

Returns an unsaved model instance

contact.save()

Saves that instance to the database

A common real-world example is assigning the currently logged-in user to a newly created record before saving it.

We'll use this concept when we introduce authentication and user-specific contacts.

Part 7 — Compare the Three Approaches

You have now encountered three different ways of handling data.

Approach

Main responsibility

request.POST

Access raw submitted values

forms.Form

Define and validate form data manually

forms.ModelForm

Define and validate form data based on a model

My recommendation for your learning path:

  • Understand ordinary Django Forms because they teach the validation lifecycle.

  • Use ModelForms for typical model-backed CRUD operations.

  • Learn raw request handling because it remains useful for custom endpoints and APIs.
